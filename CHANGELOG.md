# Changelog

## Unreleased (after the 0.4.0 candidate dbf9704)

- Independent QA fixes (Codex QA_FINDINGS 2026-10-28). QA-002: a server named `__proto__`, `constructor`, `toString` and similar was dropped or mis-read during discovery because server maps were plain objects; a `__proto__` entry granting the whole disk vanished from the scan with exit 0. Server maps are now prototype-free, so every name is an ordinary server in each client, plugins, push and `boppi fix`. QA-001: a Claude Code plugin index with any install record Boppi cannot read (relative path, invalid name, missing path) counted as complete, so a full push could replace the workspace inventory without that plugin; such an index is now `unreadable`, the scan exits 4, a push merges, the readable plugins are still scanned, and `boppi verify` leaves earlier plugin predictions unresolved. The incomplete-scan message no longer claims the whole client is missing. QA-003: `push` now refuses, before printing or sending, a body with an id that is not a Boppi id (`<kind>_<16 hex>`) or any string value or key shaped like a secret; it names the field, never the value. Ids are refused rather than rewritten so references between records stay intact. `test/verify-discovery-integrity.js` 34 checks and `test/verify-push-unsafe-fields.js` 13 checks; reverting each fix fails 12 to 14 and 9 of them.
- `boppi fix --server <name> --narrow <dir>` keeps a filesystem server and points its broad directory argument (the whole home directory, a system root, or a dotfile or secrets folder) at a folder inside it, instead of removing the server. The target must already exist, sit inside the current directory once links are resolved, and not be broad itself (narrowing home to `~/.ssh` is refused); a server with two broad directories is refused rather than guessed. The prediction comes from a rescan with the edited entry, so the preview says which paths close and which drop in priority, and the edit goes through the same hash-bound preview, lock, backup, atomic write, rescan and grading as a removal. The prediction records both directories by fingerprint and the digest of the expected entry, so `boppi verify` confirms only the exact narrowed entry, and no directory path reaches an export or push. `boppi rollback` lists and restores narrow fixes, and `boppi uninstall` waits for a live one. Command line only: the workspace cannot propose a narrow fix yet. `test/verify-narrow-scope.js`, 26 checks; resolving links with `path.resolve` instead of the real path fails 6, and leaving uninstall on removals only fails 1.
- Secret values in server arguments are now redacted whatever their vendor. Before, only a dozen token prefixes were recognized, so a Google API key (`AIza…`), a GitLab token (`glpat-…`) and 19 other formats in a positional argument reached the terminal report, HTML, JSON, SARIF and `push`. Added the real formats of Google, GitLab, GitHub (`gho_`/`ghs_`/`ghu_`/`ghr_`), npm, PyPI, Hugging Face, xAI, Google OAuth, DigitalOcean, Shopify, SendGrid, Stripe webhooks, Linear, Notion, Azure storage keys and PEM private keys, plus a prefix-less rule for keys that look random (16+ characters mixing letters and digits with high entropy, or 32+ character base64). Words, versions, UUIDs and Boppi's own path fingerprints are left alone, so re-sanitizing an export changes nothing. The workspace runs the same code on every upload. `test/verify-secret-redaction.js`, 58 checks: 27 token formats, 20 ordinary arguments that must survive, idempotency, and a whole scan of a synthetic config holding every token (terminal, JSON, HTML, SARIF, push body). The previous code fails 23 of them.
- Rate-limit answers from the connector (E-6). A workspace now limits each paired device to 300 calls per 10 minutes and answers 429 `rate_limited` with `Retry-After`; `connect` prints `retry in N seconds` and does not retry on its own (the next `connect run` cycle polls again at its interval). Unpair is never limited. `test/verify-connector.js` 88.
- Device credential rotation and self-unpair (E-5, needs the workspace's `/api/connector/rotate` and `/api/connector/unpair`). `boppi connect rotate` asks the workspace for a new device credential and stores it (owner-only); `connect run` does it on its own when 7 days or less remain. The workspace keeps the current credential valid until the new one is first used, so a lost answer or a failed write leaves the device working. `boppi connect unpair` now revokes the device in the workspace before deleting the local pairing; an unreachable workspace keeps the file so the unpair can be retried, and a credential the workspace already refuses is deleted locally with that explanation. `boppi uninstall` points at `connect unpair` and still never contacts the workspace. `test/verify-connector.js` 87 (14 new: rotation, promotion on first use, lost answer, 7-day threshold, unpair success/unreachable/already refused); disabling the threshold fails 1.
- Connector recovery: a refused pairing code says it is wrong, used or older than ten minutes; a refused device (revoked, unpaired, expired) says how to pair again, and `connect run` stops instead of polling forever; `connect pair` on an already paired machine is refused before the code is sent unless `--yes` (which also drops the old device's claims). verify-connector 93.
- `boppi uninstall` only stops for fixes still applied (a remove_server entry no rollback names, or a backup no record names), listing `boppi rollback --id <id>` for each; backups of rolled-back fixes no longer block it (it was a dead end after any fix, since rollback keeps backups). verify-uninstall 33.
- `boppi uninstall` (external beta item 4). Lists every entry under `~/.boppi` with what it is, its file count and size, the pairing (workspace named, credential never printed), and each Claude Code hook entry that runs `boppi hook` (user `settings.json`/`settings.local.json` and the project's), with file and JSON location; then deletes `~/.boppi` after confirmation (`--yes` without a terminal, `--dry-run` lists only). A directory holding fix backups is kept unless `--include-backups` is given. A linked `~/.boppi` is refused. Client settings are only read. `test/verify-uninstall.js`, 29 checks on state written by real commands (scan, hook, demo, fix, notice, pairing); removing the backup guard fails 2, removing the link refusal fails 1.
- Offline update notice (D-6). The workspace's Agent routes (ingest, events, connector) answer with a `Boppi-Agent-Minimum` header, refusals included. The Agent reads it from answers it already gets, never asks npm or another host, keeps the last value per workspace origin in `~/.boppi/update-notice.json` (owner-only: origin, minimum, time), and after each command prints one stderr line when the installed version is older: `Update: <workspace> asks for Boppi <minimum> or newer; this is <version>. Run: npm install -g boppi@latest`. Because it reads the stored file, the notice also shows on commands that make no request. An answer without the header clears that workspace, an equal or older minimum prints nothing, a malformed value changes nothing. It never changes an exit code and never prints from `boppi hook`. `NO_UPDATE_NOTIFIER` or `BOPPI_NO_UPDATE_NOTICE` silences it. `bin/boppi.js` now calls `main` (run, then the notice). `test/verify-update-notice.js`, 32 checks; routing the bin back to `run` fails 4, dropping the recording fails the suite.
- GitHub Action pinned to the package version (D-5). `version` defaults to the package version (0.4.0) instead of `latest`, and anything other than an exact version (`latest`, `^0.4.0`, `0.4`, empty) stops the step before `npx` runs. Inputs now reach the step as environment variables instead of `${{ }}` text inside the script, which closes a script-injection path (a `config` or `policy` value such as `$(...)` ran as shell code in the old step). `test/verify-action-pin.js`, 16 checks: it runs the step's real script under bash with a stand-in `npx`, fails 14 of 16 against the previous action.yml, and fails when the default drifts from package.json. Not run on a GitHub runner.
- Windows path rules (D-4). Program lookup on win32 tries each `PATHEXT` extension (default `.COM;.EXE;.BAT;.CMD`), splits `PATH` on `;`, matches names without regard to case and does not require an execute bit. A server whose program resolves to a `.cmd` or `.bat` file is refused with a message that it needs a shell (Boppi never starts servers through one) and what to point at instead, rather than reported as missing; `npx.bat` is refused as a package launcher like `npx.cmd`. Claude Desktop on win32 uses `APPDATA` only when the scanned home is the real home, so `--home` reads that home's own AppData. `test/verify-windows-paths.js`, 12 checks, simulates win32 on any OS; a new experimental `windows-latest` CI job runs it on Windows. Not yet run on a Windows machine: that job has never executed (nothing is pushed).
- Remote header names as inspect-only facts (D-3). Each server's `headers` names and the presence of a `headersHelper` are recorded on its export record (`configFacts`), and COVERAGE prints a `Not graded:` line when a server sends credential-looking headers. Header values and the helper command are never read into any output (a mutation that keeps them fails the leak check over terminal, JSON, HTML, SARIF and history). No grade changes: exposure paths and capabilities are identical with and without headers, pending the rubric. Not sent by `push`. Flagging a literal secret value would mean reading values in memory, which the current privacy wording rules out (founder decision D-41). `test/verify-config-facts.js`, 9 checks.
- Claude Code plugin MCP servers (D-2). Discovery reads `installed_plugins.json` in the documented plugins root (`~/.claude/plugins` or `CLAUDE_CODE_PLUGIN_CACHE_DIR`) and the `mcpServers` of each install's `.mcp.json` and `.claude-plugin/plugin.json`. Servers are labeled `plugin:<plugin>:<server>`, as Claude Code registers them, and graded like other servers; `enabledPlugins` and `defaultEnabled` are recorded, not graded. Plugin files are read-only to Boppi: `fix`, `plan`, remediation and the connector never locate them, and the message says to disable the plugin. An unreadable index or a `plugin.json` that points `mcpServers` at a file, bundle or URL marks the scan incomplete. Claude Desktop extensions stay undiscovered (install location undocumented) and the README says so. `test/verify-claude-plugins.js`, 23 checks; removing the read-only guard fails 3 of them, including one where fix edited a cached plugin file.

The write goes through the fix primitives under a per-file lock: reopen without following symlinks, hash recheck at the write boundary, owner-only backup, atomic write, validation, manifest entry (`boppi rollback` restores it). Failures are reported as fixed codes; the acknowledgement is never printed as a fix, and the output waits for the workspace's rescan grade. The earlier "never collected" sentence overstated the guarantee. Verify suites now reach a Cursor residual sentence and a lowered prediction graded across an agent id change (`verify-builtin-tools.js` 77, `verify-predictions.js` 34).

Not in candidate 2d65a09 (source fix only, 2026-10-25).

Every exposure path now carries an `assessment`: the template's worst-case `impact`, the `priority` the report shows, and which branch of the path is weakest. Priority is the impact stepped down by evidence strength, never up. ## 0.3.1

Local candidate additions (unpublished):

- Built-in agent tools are in the graph. Claude Code (Bash, Read, Edit, Write) and Cursor (terminal, file edits) carry shell and file access as grants on the agent itself, so Claude Code with one `fetch` server now reports the privilege path (EP-E) it always had, exfiltration paths include the agent's own file access, and removing an MCP shell server is never offered as the fix for a shell the agent keeps. Claude Code's permission settings (`~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`) grade each tool as prompts, no prompt, or denied; a whole-tool deny removes the capability. Only rule counts and the mode are recorded. The terminal and HTML reports list BUILT-IN TOOLS separately from MCP servers, the settings files appear in DISCOVERY and the privacy footer, and every prediction, plan, fix, and verify rescan includes the built-in grants, so "removing X breaks N paths" stays true. Demo scenarios now show the same paths a real Claude Code machine would.
- Unrecognized servers are named instead of silent. A server that matches no catalog entry, name rule, url, directory argument, or declared capability is tagged `unrecognized` in MCP SERVERS, listed under UNRECOGNIZED SERVERS with its launch and the reasons nothing matched, named in the COVERAGE not-established line, shown in the HTML report, exported as `recognition` in JSON, and reported in SARIF as `BOPPI-UNRECOGNIZED`. Package launches now keep their version: `npx pkg@1.2.3`, `uvx pkg==1.2.3`, and `docker run image:tag` are pinned; no version, `latest`, or a range is `unpinned` (PACKAGE PINS section, SARIF `BOPPI-UNPINNED`). A catalog server with no capability, such as the time server, stays recognized.
- Per-tool reach and file scope. Tool names from the catalog and the config map to the engine's finer categories (`push_files` modifies source, `kubectl_apply` reaches production, `slack_post_message` sends an external message, a Gmail server reads and sends email), and each filesystem directory argument is graded as the whole home directory, a system-wide directory, a dotfile or secrets folder, a source tree, or a folder elsewhere before the path is discarded. Each category becomes one more permission on the server (source id `tool-reach:<server>:<category>`), so the supply-chain path (EP-C) and the impersonation path (EP-F) now fire from real configurations, and a filesystem server at `~/` is no longer graded like one at a photos folder. The terminal report prints `file scope:` and `reach through tools:` under each server, the HTML report shows them under capabilities, and the graph carries them as server evidence. No path is recorded.
- Analysis engine 1.0.2: when two routes evidence the same exposure, the engine now prefers the one whose node labels sort first instead of the one whose record ids sort first. Record ids are content hashes that differ between machines, so the same configuration could print a different EP-A chain, and a different prediction set, on two machines. Chains and predictions are now identical for identical configurations.
- Four report corrections from the validation-kit run. `boppi verify` no longer says "Nothing could be graded yet" when one edit is confirmed and another was not applied; the next-step line names both. ROOT CAUSE and `boppi plan` list an edit only for the configuration files that hold that server, instead of every file of the client (discovery now records which server keys each file holds, names only; older exports fall back to the previous behaviour). Graph permission boxes carry plain-word labels such as `file access (the whole home directory)` or `modify source code`, with the raw permission text and tool names kept in the node's evidence. In the demo page, the counters and the "Understand the exposure" card always describe the sample's actual scan; a simulated removal changes only the Preview counter, the graph, and the inventory, and the card says a simulated preview is active instead of claiming the sample has no paths.
- Collector version/platform and discovery coverage are transported through scan exports and pushes. Selected or incomplete scans merge safely; older files do not inherit a fabricated producer version. Dry runs show the envelope, and redirects are refused.
- Exact-identity MCP catalog with capability/tool provenance; analysis engine 1.0.1 marks catalog-derived reach as inferred.
- Synthetic interactive browser demo with shared graph evidence, removal previews, and reset.
- Sanitized `plan --diff`, integrity-checked local backups, staged fixes, and rollback that protects later configuration changes.
- Optional, manually configured local hook capture with bounded inputs and retention; no automatic installation or runtime upload.

- `boppi push` sends `snapshot_at` (the export's `exportedAt`) with every snapshot, so the workspace can refuse a snapshot older than the one it already holds from this machine. An export without a timestamp is still pushed, without the field.
- A `409 stale_snapshot` rejection prints the server message and the time of the snapshot the workspace kept; a `429 rate_limited` rejection prints the server message and how many seconds to wait (from the body, or the `Retry-After` header). Both exit 5, like every other rejected push. The client never retries on its own.
- `boppi plan` prints the POLICY section and exits 1 when `boppi.policy.json` (or `--policy`) is violated, the same as `boppi scan`. Before, it evaluated the policy and ignored the result.
- `boppi scan` ends its terminal report with a `boppi push` hint.
- Docs: the local history file keeps the last 40 entries, not 20 as the 0.2.0 notes said; `boppi plan` and `boppi fix` are listed with the commands that make no network requests; the Linux Claude Desktop path is in the discovery table.

## 0.3.0

- `boppi plan`: compare every candidate fix side by side (paths broken, new paths it would create, capabilities the agent loses) and print the exact file and key for each edit. Changes nothing.
- `boppi fix --server <name>`: remove one server entry from the config that holds it, after a mode-600 backup under `~/.boppi/backups/` and a confirmation (`--yes` for scripts), save the predictions it used, rescan, and grade the result. Exit 0 means CONFIRMED.
- Predictions now simulate moving a server between clients, rescanned on both the source and the target, and every prediction names the capabilities the agent would lose that no other server provides. Ranking prefers fewer new exposures and less lost capability.
- `boppi history` reports verified exposure reduction: eliminations confirmed by `verify` or `fix` that are still absent from the latest scan.
- Policy guard: `boppi.policy.json` in the working directory (or `--policy <file>`) declares denied servers, capabilities, capability combinations, an allow list, a severity floor, and whether unrecognized servers are allowed. Violations print in a POLICY section, land in the JSON and SARIF exports, and exit 1. Unknown keys and invalid values exit 2.
- `--sarif <file>` writes a SARIF 2.1.0 report with the exposure templates, findings, and policy rules as rules, using portable config paths.
- A GitHub Action (`action.yml`) runs the scan on a repository's MCP config in CI and can upload the SARIF to code scanning.
- The secret-value redaction now requires a boundary before each token prefix, so package names such as `@wonderwhy-er/desktop-commander` are no longer redacted and can be matched by a policy.
- `npm test` proves that every command except `push` makes no network request: the suite runs each command with sockets, DNS, and `fetch` disabled.

## 0.2.0

The free beta release.

- `boppi push`: send one scan's sanitized inventory to a Boppi workspace with a collector token (`npx boppi push`, then paste the token at the hidden prompt; `BOPPI_TOKEN` or `--token` for scripts). This is the only command that uses the network. It sends agent, MCP server, permission, and integration records as a snapshot, so a machine that gets fixed shows up fixed. `--dry-run` prints exactly what would be sent; `--file` pushes an earlier `--json` export; `--merge` keeps records absent from the scan.
- `boppi history`: the last 40 local scan summaries and what changed between them. Scans now record a sanitized summary in `~/.boppi/history.json`; `--history-file` moves it.
- Credential arguments are redacted. Values that look like tokens, keys, bearer or JWT values, or connection strings with embedded passwords; the value after a flag whose name says credential (`--api-key x`, `--token x`, `-p x`); and the value side of `--key=...` or `NAME_PASSWORD=...` never reach a model, export, history file, or verifier bundle. Previously only env values and flag names were protected, and the value after `--token` went through untouched.
- The report gains an MCP SERVERS table, a COVERAGE section that separates what the scan established from what it cannot know, a CHANGES SINCE LAST SCAN comparison, and a NEXT STEPS footer that names the exact `boppi verify` command for the export you just wrote.
- `boppi verify` explains each grade in plain words next to its reason code and ends with the next action. Contradiction fixture names are sanitized and proven to stay inside the output directory.
- Argument errors are no longer silent: an unknown `--only` client or a missing `--config` file exits 2 with the reason instead of reporting a clean machine. A config that is a directory or unreadable says so instead of "invalid JSON". A config rejected for secret material says what to do about it.
- Path fingerprints are keyed with a per-machine secret (`~/.boppi/fingerprint-key`, created once, owner-only), so a common path such as a home directory cannot be recovered by hashing guesses. Fingerprints stay stable on one machine and differ across machines.
- A clean scan ("no exposure paths") no longer says "good sign". It says it is not proof the environment is safe.
